2.1. Використання окремих гілок для виконання завдань (Feature Branches / Git-flow):
--------------------------------------------------------------------------------
1. Ізоляція кодової бази та середовища розробки:
   Кожен розробник працює над конкретним функціоналом (feature), рефакторингом або 
   виправленням дефекту (hotfix/bugfix) у власній ізольованій гілці (наприклад, lz2-humelnyk).
   Це гарантує, що незавершений, експериментальний або зламаний код не впливає на стабільний 
   стан базових інтеграційних гілок (main / staging / develop / kn1-m25).

2. Паралельна командна розробка без взаємних блокувань:
   Кілька інженерів можуть одночасно розробляти незалежні модулі системи. Гілки дозволяють 
   інтегрувати або відкочувати окремі задачі за допомогою стандартних операцій Git (merge, rebase, 
   cherry-pick, revert), не створюючи затримок для інших членів команди.

3. Прозорість історії змін та полегшення аудиту:
   Історія версій залишається структурованою та атомарною: один логічний блок змін відповідає 
   одній гілці. Це значно спрощує відстеження регресійних збоїв за допомогою утиліти `git bisect` 
   та локалізацію проблем у життєвому циклі ПЗ.

--------------------------------------------------------------------------------
2.2. Захист гілок від злиття без проходження код-рев'ю старшими розробниками 
     (Branch Protection Rules & Peer Review):
--------------------------------------------------------------------------------
1. Архітектурний контроль та дотримання стандартів якості коду:
   Правила захисту гілок (Branch Protection Rules на GitHub/GitLab) вимагають обов'язкового 
   схвалення (Approval) від щонайменше 1–2 уповноважених спеціалістів (Tech Lead, Senior Dev, QA Lead).
   Це запобігає проникненню у спільне сховище антипатернів, надмірної алгоритмічної складності, 
   порушень принципів SOLID/DRY та недотримання узгодженого стилю коду (Code Conventions).

2. Запобігання витоку конфіденційних даних та порушенням безпеки:
   Рев'ювери перевіряють відсутність hardcoded-паролів, API-ключів, персональних даних та відкритих 
   вразливостей (SQL injection, XSS тощо) перед тим, як код потрапить у загальнодоступну гілку.

3. Обмін досвідом та командна взаємодія (Knowledge Sharing):
   Процес код-рев'ю слугує ефективним інструментом менторства та взаємного навчання. Менш досвідчені 
   розробники отримують зворотний зв'язок від сеньйорів, а вся команда залишається обізнаною щодо змін 
   у різних частинах архітектури додатку.

4. Захист від людського фактора та руйнівних дій:
   Branch Protection блокує можливість випадкового або зловмисного переписування історії комітів 
   через команди `git push --force`, а також випадкового видалення ключових гілок репозиторію.

--------------------------------------------------------------------------------
2.3. Для чого необхідний CI/CD процес та яке значення він має в управлінні проєктами:
--------------------------------------------------------------------------------
1. Сутність та призначення CI/CD:
   - Continuous Integration (CI, Неперервна інтеграція): автоматизований процес регулярного злиття 
     коду всіх розробників у спільну гілку, що супроводжується автоматичною збіркою проєкту (build), 
     перевіркою статичними аналізаторами коду (Linters, SonarQube) та виконанням комплексу автотестів 
     (Unit, Integration, E2E тестування на Playwright).
   - Continuous Delivery / Deployment (CD, Неперервна доставка/розгортання): автоматизоване 
     розгортання валідних збірок на тестові (staging) або продуктивні (production) сервери без 
     необхідності ручного втручання.

2. Значення для Project Management (Управління проєктами):
   - Зменшення показника Time-to-Market: швидкість доставки нової функціональності кінцевим клієнтам 
     зростає в рази, оскільки усуваються рутинні ручні операції тестування та деплою.
   - Реалізація концепції Shift-Left Testing: дефекти виявляються на найбільш ранньому етапі (в момент 
     створення Pull Request), коли вартість їх виправлення є мінімальною.
   - Прозорість метрик та контроль якості: керівник проєкту (PM) і стейкхолдери мають реальний автоматичний 
     моніторинг стану системи за показниками збірок (Build Status) та відсотку проходження тестів (Test Pass Rate).

3. Реальний приклад застосування:
   Розглянемо мобільний банківський застосунок або платформу електронної комерції (наприклад, 
   Rozetka, monobank або Bolt). 
   - Сценарій без CI/CD: Розробник оптимізує алгоритм розрахунку персональних знижок та кешбеку. 
     Локально зміна працює, але внаслідок конфлікту версій бібліотек ламається модуль онлайн-еквайрингу 
     (обробки банківських карток). Зміна потрапляє в реліз без автоматичних перевірок, користувачі не 
     можуть сплатити за замовлення, компанія за лічені хвилини зазнає мільйонних збитків і втрачає репутацію.
   - Сценарій із налаштованим CI/CD: При створенні Pull Request пайплайн у GitHub Actions автоматично 
     піднімає ізольований тестовий контейнер, запускає лінтери та набір автотестів Playwright, що 
     імітують реальні транзакції. Тест виявляє збій на кроці перевірки платіжного шлюзу. Збірка позначається 
     як FAILED, автоматичне злиття блокується. Дефект виправляється розробником за 10 хвилин, а клієнти 
     отримують виключно стабільний і безпечний сервіс.
